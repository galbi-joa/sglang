## 1. 출발점 (멘토 claim)

> "On B300, FlashMLA is much slower than trtllm-gen in the CP scenario.
>  먼저 claim 확인 → profile로 차이 분석 → FlashMLA 최적화."

이걸 그대로 믿고 벤치부터 짜는 게 아니라, **"SGLang에서 이게 실제로 무슨
뜻인지"** 부터 코드로 한 겹씩 풀었다.

## 2. 코드 분석으로 확정한 사실 (실측 전)

1. **FlashMLA와 trtllm-gen은 교체 가능한 두 attention 백엔드**
   (`--attention-backend flashmla` vs `trtllm_mla`).
2. **trtllm-gen 호출점은 flashinfer다** — `trtllm_mla` 백엔드는 얇은 래퍼고,
   실제 커널은 `flashinfer.decode.trtllm_batch_decode_with_kv_cache_mla(...)`.
3. **CP는 모델 레벨의 일이지 커널 기능이 아니다** — latent KV all-gather는
   `deepseek_v2.py:rebuild_cp_kv_cache`에서 일어난다. 커널은 CP를 모른다.
4. **그래서 비교 대상 = CP 배포에서 도는 attention 커널** (decode / prefill).
5. **FlashMLA는 prefill도 자기 decode 커널로 처리**한다 (absorbed-MLA 경로).
6. **#1 가설**: `sgl-kernel/cmake/flashmla.cmake`가 dense decode를 sm90만
   빌드 → B300(SM10x)엔 dense decode 커널이 없을 것.

## 4. B300 실측 — 노가다 구간

| # | 시도 | 결과 |
|---|------|------|
| 1 | `--dtype bf16` decode | flashmla `BF16 Dense MLA is not supported on SM100` → 가설 #6 확정 |
| 2 | `--dtype fp8` decode | flashmla `no kernel image` (fp8 dense도 sm90 전용) + trtllm JIT 실패 |
| 3 | trtllm JIT 실패 원인 | `nvcc fatal: Unsupported gpu architecture 'compute_103a'` |
| 4 | 환경 진단 | nvcc **12.8** (compute_103 미지원), 드라이버 **580.126 (CUDA 13 OK)** |
| 5 | **CUDA toolkit 13.0 설치** | nvcc 13 → compute_103 지원 → **trtllm-gen JIT 통과, B300에서 작동** |
| 6 | trtllm 단독 테스트 | `TRTLLM OK` (block_num 2의 배수 제약 맞춘 뒤) → trtllm 베이스라인 확보 |
| 7 | flashmla sparse decode | 여전히 `no kernel image` |

## 5. 핵심 발견 (정정 포함)

### (a) trtllm-gen이 B300에서 안 됐던 이유 = 환경
- 설치된 CUDA toolkit이 **12.8** → `compute_103a` 미지원 → flashinfer JIT 실패.
- **드라이버는 이미 580.126 (CUDA 13 지원)** 이라 toolkit만 13으로 올리면 됨.
- → `cuda-toolkit-13-0` 설치로 **trtllm-gen 작동 확정**.

### (b) FlashMLA가 B300에서 안 됐던 이유 = wheel이 옛날 빌드  ★중요 정정★
- 처음엔 "FlashMLA는 B300에서 아예 못 돈다"고 결론냈으나 **틀렸다.**
- `sgl-kernel/cmake/flashmla.cmake`를 보면 **CUDA > 12.8이면 SM100을,
  CUDA >= 13.0이면 SM103를 빌드**하도록 돼 있다 (`FLASHMLA_ENABLE_SM100`).
- 우리가 쓴 `sgl_kernel`은 **pip prebuilt wheel** — 누군가 CUDA ≤12.8에서
  빌드해서 **sm100/sm103가 안 들어간** 채로 패키징됐다.
- 방금 깐 CUDA 13은 flashinfer JIT용 nvcc만 13으로 바꿨을 뿐, **이미 설치된
  sgl_kernel wheel은 그대로 옛날 빌드.** 그래서 flashmla는 sm90 바이너리만 갖고
  있어서 `no kernel image`.
- → **해법: sgl_kernel을 CUDA 13으로 소스에서 재빌드하면 SM100 커널이 들어간다.**

### (c) 단, dense decode는 재빌드해도 안 된다  ★최종 결론★
- cmake의 `FLASHMLA_ENABLE_SM100` 블록을 보면 SM100용 소스는:
  - dense **prefill** ✅, sparse **prefill** ✅, sparse **decode** ✅
  - **dense decode ❌ (소스 자체가 없음)**
- 즉 재빌드하면 B300에서 **sparse decode/prefill, dense prefill은 살지만,
  dense decode는 FlashMLA 소스에 아예 없어서 못 만든다.**

## 6. 멘토 claim의 최종 진단

> "B300에서 FlashMLA가 trtllm-gen보다 느리다"의 실체:
> - **dense decode**: FlashMLA는 SM100 소스 자체가 없음 → 느린 게 아니라 **없음**.
>   trtllm-gen만 작동.
> - **sparse decode (DSA/V3.2)**: FlashMLA가 지원하나, **wheel을 CUDA 13으로
>   재빌드**해야 B300에서 돈다.
> - trtllm-gen은 **환경(CUDA 13)** 만 맞추면 B300에서 작동.

## 8. 배운 것 / 시행착오

- **prebuilt wheel의 빌드 환경**이 실제 런타임 GPU와 다르면 "no kernel image"가
  난다. cmake가 지원해도 wheel이 옛날이면 소용없다.
- **CUDA error는 try/except로 잡아도 컨텍스트가 오염**돼서 이후 GPU 호출이 다
  깨진다. 벤치에서 백엔드별로 분리 실행이 필요.
- **드라이버 vs toolkit은 별개**다. 드라이버(580)가 CUDA 13을 지원해도 toolkit
  (nvcc)이 12.8이면 신규 아키(SM103) 컴파일 불가.
- claim을 곧이곧대로 "느리다"로 받지 말 것 — 실측하니 "느림"이 아니라
  "커널 부재 + 빌드 환경 문제"였다.
